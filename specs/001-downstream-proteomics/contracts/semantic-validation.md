### Preimplementation configuration migration

No maintained consumer of the former draft schema exists at the baseline. This candidate moves study.assay→assay, study.taxonomy_id→organism.taxonomy_id, input.scale→source_scale, the primary designs[] member→design, remaining members→additional_designs, and families→multiplicity_families. Models and contrasts remain explicit, with canonical primary-engine/hypothesis declarations added. Family endpoint is renamed hypothesis_type; model hypothesis effect-threshold spelling is standardized to treat. No automatic old/new mixed-field parsing is authorized: schema_version=1.0.0 and obsolete fields fail with E_CONFIG_SCHEMA and a migration explanation. This correction changes a draft contract, not existing analysis data or FR identities; see ADRs 0001–0003. Historical runner inputs are unaffected.

A row's `n_obs_by_required_group` is a JSON object keyed by the planned required groups, counting genuinely observed biological units, not injections. A group not involved in an endpoint is not smuggled into its effective n. For a continuous-covariate endpoint required_groups explicitly lists all analyzed groups and its estimand states the covariate effect. Mapping or descriptive operations with no contrast use null, plus a reason, rather than a made-up sample count.

### Precision weights

An omitted model.precision_weights means no supplied weights; the examples explicitly use kind=none. kind=observation requires a TSV with observation_id and weight; kind=matrix requires the same feature/observation keys and layout as the canonical abundance matrix. Every used weight must be finite and positive. Align by IDs and freeze weight bytes/hash with the model; missing weight entries cannot silently become one. Only the qualified limma route accepts these weights in this version; DEqMS/proDA weight requests fail their named design-eligibility errors. These checks produce WeightValidation and ExactContrastDiagnostics (no family) and are tested by V037/V042/V054.

A required inferential plan with no eligible protein features returns E_NO_ELIGIBLE_FEATURES/exit 2, while a separately requested QC-only scope may complete descriptively. Zero eligible tests is not a successfully fitted zero-discovery analysis. This produces CoverageResult/EligibilityDecision (no family) and is tested by V020/V024/V050.

`model.execution_requirement` is configuration intent, not an installation probe. `role=primary` with `execution_requirement=optional` is structurally invalid. A sensitivity model may be required or optional, but omission is forbidden: there is no environment-dependent default. Scientific inapplicability is evaluated from assay/design/data rules and may reject a required plan or mark an optional endpoint INAPPLICABLE. Only after that decision does doctor/planning inspect implementation, binary, package and resource availability. An optional, scientifically eligible but operationally unavailable model stays requested in the frozen plan with state NOT_RUN and forces PARTIAL/nonzero if execution proceeds; it cannot disappear during validation or be relabeled INAPPLICABLE.
